# Hosted native registry

Phase 5 registry unit, unreleased. The complete stateless hosted path remains gated on the remaining operational stores and Phase 4 commit/effect protocol. This unit does not enable buffered production acceptance or remove `shared_local_cleanup_pending`.

Standalone keeps its SQLite source/catalog/deletion/cleanup records, storage binding, inode checks and checkpoint behavior. Hosted native stores use `pc_native_sources` and `pc_native_projects` in the catalog PostgreSQL database, without opening `registry.sqlite`. Scratch directories and engine handles are disposable process state. A source ID and its original storage fingerprint must match authoritative PostgreSQL state. Changing worker directories cannot choose another identity or namespace.

`internal/lake/native_registry_migrations.go` owns numbered catalog-registry steps. It preserves the pre-versioning definitions as version 1 and adopts only their recognized columns, defaults, keys and foreign key. Unknown unversioned formats and future versions are refused. Later fields and constraints append steps. Application journal/control and native data-schema migrations retain their separate owners; lake does not import porcupine. A directory containing an older local registry is refused with an explicit offline-inventory/cutover requirement. No online journal migration or extra worker-registration protocol is introduced.

The typed registry exposes source binding, lookup, bounded ordered discovery, authorized bootstrap registration, ready state, permanent deletion fences and cleanup attempts. Lookup and discovery never insert a project or initialize a native schema. Discovery retains terminal records for recovery and never depends on which catalogs a worker has opened. Phase 4 owns privileged cold opening, sealed-stream recovery/ACK and native state predicates. A registry lookup alone is not permission to create or reopen a stream.

Cleanup scheduling and status read PostgreSQL for cold catalogs. Claims serialize selection and carry a new attempt ID; completion compares that ID so a late worker cannot overwrite a newer recovery outcome. An abandoned attempt becomes eligible at its stored retry time. Startup does not reset other workers' active claims. Failed or read-only cleanup cannot record success, and status from another worker sees the same durable result. Attempt IDs protect scheduling/status; expiration is not proof that old native work stopped. Native serialization/fencing and reader/restore retention remain separate requirements.

Deletion keeps control intent distinct from native completion. The full hosted protocol must seal the native stream, retain its final effect sequence, reconcile through that sequence and drain readers before marking it purgeable/deleted. This registry unit preserves existing native deletion behavior and permanent metadata fences; it does not rewrite Phase 4's seal/fence implementation or claim all project jobs have moved. Unreconciled restore artifact holds and unknown ownership stay pending. No logical status certifies physical removal of applicable S3 versions or backups.

Evidence includes real PostgreSQL migration/adoption/future-version tests, stale cleanup completion and read-only refusal, plus two cold workers with no local registry, shared maintenance/status, deletion without reopening, isolation of another project, binding mismatch, scratch replacement and explicit legacy cutover refusal. Timings are correctness evidence, not comparative benchmarks.

The [native recovery and seal unit](hosted-native-recovery.md) adds existing-only sealed proof recovery and publication ACK. Legacy mutation, maintenance and deletion paths now refuse hosted catalogs until their common guarded lifecycle is implemented. This does not claim physical purge or prune permission.
